# omp-todo-ng

English | [简体中文](README.zh-CN.md)

- **The `todo` tool**
  - `todo` tool registration — Does: registers a tool named `todo` that shadows the host's built-in tool, accepting a flat JSON object (`goal`, `add`, `start_id`, `explain`, `estimate`, `done_id` with an optional `commit`, `drop_ids`, or `view`) over a phased list with a goal, stable item IDs (`t1`, `t2`, …), per-item explanations, minute budgets and per-status progress times. Calling `todo({})` or `todo({ view })` inspects the full, current, or single-phase tree read-only; mutations return a compact active view with IDs, the current clock time and the active item's target completion time. When: whenever the model calls `todo` in a session where the plugin is loaded. Example: `pi.registerTool(TODO_TOOL_DEFINITION)` in `index.ts`; inspect with `{}` / `{ view: "current" }`, or mutate with `{ goal: { title, summary, acceptance }, add: [{ phase, title, detail, minutes }] }`.
  - Tool field declarations — Does: declares `loadMode: "essential"`, `approval: "read"` (Plan Mode compatible), `concurrency: "exclusive"` and `mergeCallAndResult: true`, so the tool is always available, serialized and its result card replaces the call card. When: fixed at tool registration on plugin load. Example: `TOOL_FIELDS` in `index.ts`.
  - Description and card rendering — Does: carries a concise (<=200-char) description summarizing phased work, the per-item `leafMaxMinutes` limit, and `todo({})` / `todo({ view })` inspection, plus `describeCall`/`describeResult` and `renderCall`/`renderResult` hooks that paint ANSI and native cards previewing the structured arguments and delta/full state. When: in the tools section of the prompt whenever `todo` is offered, and when a `todo` call or result card renders. Example: `DESCRIPTION` in `src/tool.ts`, `renderTodoCall`/`renderTodoResult` from `src/render.ts`.
  - Batch validation — Does: validates the entire call atomically before applying anything: non-empty goal/task fields, unique titles, positive integer `minutes` capped by `leafMaxMinutes` (default 60), valid IDs, and `commit` only alongside a `done_id` that completes an open item. When: on every `todo` call, before any state change. An `add` allocates its IDs before validation, so the same call's `start_id`, `explain`, `estimate`, `done_id` and `drop_ids` may name them. Example: `validate`/`overCap` in `src/kernel.ts` produce `Task "…" estimate 90 min exceeds the 60-minute limit for one item`.
  - New round after a finished list — Does: once every item is completed or abandoned, a call with `add` starts a new round instead of appending: the finished goal and items are not carried over, IDs restart at `t1`, and the call must carry `goal`, otherwise the whole call is rejected. Calls without `add` still act on the finished list. When: on a `todo` call with `add` while the list has no `pending` or `in_progress` item. Example: `planTodo` with `roundOf` in `src/kernel.ts`; `{ add: [...] }` alone is rejected with `Every item of this list is completed or abandoned, so add starts a new round … provide goal together with add`.
  - Transition pipeline — Does: runs every `todo` change through fixed stages: structural planning of the call, the tail-item transform, synchronous guards (tail-item lifecycle, overtime estimate lock), asynchronous acceptance guards, then the completion-commit guard, and writes the list only after all of them allow it. The first refusal or exception rejects the whole call with `isError`, skips every later guard and leaves the host list, the notes and git as they were; an allowing guard may add a note to the result or a state change applied when the list is written (the commit record). Asynchronous guards receive the tool call's `AbortSignal` and `ExtensionContext`; each refusal is logged as a warning with the guard's name. When: on every `todo` call that changes the list, once the project config parsed. Example: `planTransition`/`runGuards` in `src/pipeline.ts`, guard types in `src/guard.ts`, planning in `src/kernel.ts`; a guard that throws yields `Guard "<name>" failed: <message>`.
  - Overtime estimate lock — Does: refuses an `estimate` that changes the minutes of an item whose budget already received an overtime warning, telling the model to add the remaining work as new items; off when the project config sets `effects.overtime` to `false`. When: in the synchronous guard stage of a `todo` call carrying `estimate`. Example: `overtimeLock` in `src/pipeline.ts`, error `Task "…" (t1) already received an overtime warning, so its 10-minute estimate is closed and estimate cannot change it. …`.
  - Project tail items — Does: when a call starts a list or a new round, appends the project config's `tailItems` that reach the calling agent — `main` only in the main session, `isolated` also in a subagent working in its own worktree, `all` in every agent holding `todo` — after the call's own items in declaration order, each in its `phase` with `detail` as its explanation and `minutes` as its estimate (unset: the smaller of 15 and `leafMaxMinutes`; a set value is not capped by `leafMaxMinutes`), and records `tailRule` `{ ruleId, protected }` in the notes, kept across reloads and `/todo-ng` edits; views mark such items `project rule "<id>"` and `protected`. An `add` that repeats a tail title rejects the call. A protected tail item cannot be dropped; a tail item whose current rule has a `check` cannot be completed while an item outside the tail items stays pending or in progress after the same call; once its rule is gone from the config, or the file is gone, it completes with a note. When: on the `todo` call that starts a list or a round, and on `drop_ids`/`done_id` naming a tail item. Example: `appendTailItems`/`tailLifecycleGuard` in `src/tail.ts`, errors `Task "All tests pass" is appended automatically by project tail rule "tests": remove it from add` and `Task "All tests pass" (t3) is a protected tail item from project rule "tests": it cannot be dropped, complete it instead`.
  - Tail-item checks — Does: when `done_id` completes a tail item whose current rule carries a `check`, runs the check as the acceptance guard, before the completion commit, and keeps the item open with `isError` unless it passes. A `shell` check runs `command` through omp's native shell (no `sh`/`bash` child process) in the session directory with the rule's `timeoutMs` and the tool call's `AbortSignal`, and passes only on exit 0; a non-zero exit, a missing exit status, a timeout or a cancel refuses with the cause and the last 4000 characters of output, and every run is logged with exit code and duration. A `judge` check asks the models of the model role `@omp-todo-ng` (only when bound explicitly), then `default`, in order, skipping a model that errors, with `prompt` as the acceptance condition plus the item, the list before this completion and git `status --short`, `diff --stat HEAD` and `log --oneline -5` of the session directory; it passes only when the answer holds one JSON object `{"verdict":"pass","reason":…}` (text around the object is ignored). No bound online model, a `fail` verdict, an answer that does not parse, every model failing, the `timeoutMs` deadline or a cancel refuses. Items without a check — work items, tail items of a rule without `check`, or of a rule gone from the config — run neither. When: in the acceptance stage of a `todo` call whose `done_id` completes such a tail item. Example: `acceptanceGuard`/`runShellCheck`/`judgeVerdict` in `src/acceptance.ts`, wired in `executeTodo` in `index.ts`; error `Task "Verify" (t2) stays open: the check of project rule "verify" did not pass: \`bun test\` exited with 1 in /repo.`
- **Completion commits**
  - Commit on completion — Does: `done_id` completes one item per call, because one completion owes at most one commit; its `commit.message` commits the changes the host's change record attributes to this agent and its subagents, or with `commit.paths` every change in those git pathspecs resolved from the session directory, through the host's selective commit on a private index so another writer's staged or unstaged changes stay where they are, and records `{sha, message, scope}` on the item. The commit runs as the last guard of the call, after validation and every other guard allowed it; a failed commit rejects the whole call and leaves the item open. With `effects.commit` set to `false` in the project config, a completion neither commits nor refuses, and a `commit` clause is ignored with a note. When: on a `todo` call whose `done_id` completes an open item. Example: `{ done_id: "t2", commit: { message: "feat: add export", paths: ["src/export.ts"] } }` → `Committed 1a2b3c4 "feat: add export" (src/export.ts)`, via `commitGuard`/`completeWithCommit` in `src/commit-guard.ts` and `commitCompletion` in `src/git.ts`; with commits off, `The project config turns completion commits off (effects.commit is false): the commit clause was ignored and nothing was committed.`
  - `Model:` trailers — Does: appends one `Model: <provider>/<id>` trailer per model that answered in the session since its previous todo commit, in order of first use, plus the current model. When: on every commit a completion makes. Example: `commitMessage`/`participatingModels` in `src/models.ts` write `Model: anthropic/claude-opus-5-5`.
  - Uncommitted-work refusal — Does: rejects a `done_id` without `commit` while this agent has uncommitted changes in the checkout, or while the session keeps no change record and the checkout is dirty; another writer's changes alone never trigger it, and `effects.commit: false` in the project config turns it off. When: on a `todo` call whose `done_id` completes an open item without `commit`. Example: `workState` in `src/git.ts`, error `Task "Implement" (t1) would leave this agent's uncommitted work in /repo: call todo again with commit ({ message }) …`.
  - Shared-worktree exemption — Does: lets a subagent whose cwd is in its parent agent's git worktree complete items without committing or the refusal, any `commit` ignored, so the parent integrates and commits; a subagent in its own linked worktree commits normally. When: on every completion of a subagent whose parent session resolves through `AgentRegistry`. Example: `parentCwdOf` in `src/session.ts`, `worktreeScope` in `src/git.ts`, note `Shared worktree with the parent agent (/repo): this completion committed nothing; …`.
- **List state on the session branch**
  - Host list and notes — Does: keeps the list's phases, titles, order and statuses only in the host list (`session.getTodoPhases()` live; on the branch, the latest `todo` result's `details.phases`, or the `user_todo_edit` entry the host records in place of a `todo` result when the tool is called from eval) and records only what the host list cannot hold — goal, item IDs, explanations, estimates, progress times, commit records and the tail rule of a project tail item — as a `mouriya.omp.todo-more.notes` entry joined to host items by phase name and title once, at the join; everything after the join identifies items by ID; a `todo` call writes the host list and appends a notes entry only when the notes changed; a `/todo-ng` save does the same (`commitTodoState`), the host list's content staying as it was since an edit changes only goal or explanations. Readers that act between a `todo` call's end and its result reaching the branch (the `edit` gate, the planning snapshot, the review read, the stop-time reminder check, the content of a host reminder not yet persisted) read `liveState`, and so do the `/todo-ng` panel and HUD. A `todo` result's `details.more` snapshot only feeds its own card. When: after every accepted `todo` call and `/todo-ng` save. Example: `commitTodoState`/`liveState` in `src/commit.ts`, `joinHost`/`toNotes` in `src/state.ts`.
  - Branch fold — Does: folds every read forward over the branch entries — the latest host list, from a `todo` result or a `user_todo_edit` entry, joined with the latest notes entry by phase name and title, giving a host item without notes a fresh ID and no explanation or estimate — together with ask waits, overtime warnings and the planning deliveries, keeping one incremental accumulator per session manager. When: on every read of the list by reminders, the UI and the overtime facts. Example: `foldEntry`/`branchFacts` in `src/branch.ts`.
  - Time tracking — Does: tracks per-item `in_progress` wall time with `ask` waits excluded, keeps each item's progress in a form fixed by its status (pending: first start and pause time; in progress: first start and running clock; completed or abandoned: first start and close time), converts a started item's remaining budget into a target completion clock time (`due by HH:MM`, pausing on skip/preemption and reconverting remaining budget on resume while leaving unstarted items without a deadline), and records a budget id per estimate so an overtime warning latches to that budget identity across re-estimates. When: during each branch fold, transition settlement and overtime check. Example: `elapsedOf`/`dueAt`/`transition` in `src/state.ts`, `itemTimeSummary` in `src/format.ts`, waits folded from `tool_execution_start` records in `src/branch.ts`.
- **`todo` restoration in editing subagents**
  - Subagent `todo` restoration — Does: puts `todo` back into a subagent session whose enabled tools include `edit` but not `todo`, writing the active set in canonical order (builtins in registry order, then the rest sorted by code point) so forks keep the prompt cache; tool-restricted sessions get it via `refreshRpcHostTools`. Skipped while the project config sets `effects.editGate` to `false`; an invalid project config keeps the restoration. When: before every model call of a subagent session, via a before-model-call hook armed on its first `before_agent_start`. Example: `guardSubagent`/`restoreTodo` in `index.ts`, with `canonicalToolOrder` from `omomp-shared/active-tools.ts`.
- **Planning and reminders**
  - Eager prelude content — Does: when the host's `todo.eager` (`preferred` or `always`) makes it emit its hidden eager prelude, replaces the text with the plugin's structured `todo` call instruction (`goal` and `add` with `phase`, `title`, `detail`, `minutes`); the host owns when it appears, including after an auto-compaction. When: in the `context` hook, on a message of type `eager-todo-prelude`. Example: `eagerTodoText`/`hostReminderOf` in `src/reminders.ts`, text ``Before substantive work, create a phased todo. … You MUST call `todo` first in this turn.``.
  - Edit guard — Does: blocks an `edit` call from the host's `tool_call` event while the todo list has no open item — it is empty, or every item is completed or abandoned — giving the init reminder or the finished-round reminder as the reason, without touching the host's `edit` tool. The project config's `effects.editGate: false` turns the guard off; while the project config is invalid, every `edit` is blocked with the config file path and the reason, open items or not. A `todo` call that precedes the `edit` in the same assistant message — the host emits every `tool_call` of a message before executing any of them — counts when its arguments pass `todo`'s own schema and rule checks and leave a list with a `pending` or `in_progress` item; the call is only previewed, never executed. When: on every `edit` `tool_call` of a main session or subagent; the earlier `todo` calls are checked on their own `tool_call`. Example: `registerPlanning` in `src/planning.ts` blocks with `Todo is empty. Work phase … call todo with goal` or `Every item of this todo round is completed or abandoned, so the round is over. …`, `previewTodo` in `src/tool.ts` runs the same planning, tail transform and synchronous guards against the project config, leaving out the acceptance and commit guards; an invalid config blocks with `Project config /repo/.omp/todo-ng.json is invalid: … Fix the file before retrying edit.`
  - Planning reminder — Does: delivers a `<system-reminder source="omp-todo-ng/planning">` carrying the current clock time — the `goal` + `add` instruction while empty, the instruction to start a new round with `goal` + `add` once every item is completed or abandoned, a compact active view (goal, progress, closed phase counts, `in_progress` full explanation and target completion time, plus `pending` IDs/titles and `todo({})` / `todo({ view })` hints) when semantic state changed before a user prompt or after an out-of-band `/todo-ng` edit (highlighting edited pending explanations), and the complete unabridged plain-text list once after compaction or branch transition drops prior context (headed by the new-round instruction when every item is closed) — skipping duplicate injection after `todo`'s own tool results and ignoring wall-clock ticks when semantic state is unchanged. Each delivery appends a `mouriya.omp.todo-more.planning` entry with the delivered state's key; the branch fold reads those entries, compaction and branch-summary entries and `todo` results to decide what the model last saw and whether recovery is due. When: as a hidden `before_agent_start` message when semantic state changed or context was compacted, and as `tool_result` `additionalContext` only for mid-run compaction recovery or out-of-band edits. Example: `registerPlanning` in `src/planning.ts`, `semanticStateKey` in `src/state.ts`, `foldPlanning` in `src/branch.ts`, `formatCompactView`/`formatFullView` in `src/format.ts`.
  - Stop reminder content — Does: when the host sends its stop reminder (`todo.reminders`, at most `todo.remindersMax` times, main session and subagents alike), replaces the text with the plugin's: current clock time, every open item with its ID, explanation and clock-time status (`due by` for active, `paused` for preempted, no deadline for unstarted), the goal (or a prompt to pass `goal`) and an `explain` hint for items without an explanation. The text comes from the list and message timestamp as they stood where the reminder sits in the branch, so it keeps its bytes on later requests. When: in the `context` hook, on a developer message shaped like the host's `You stopped with N incomplete todo item(s)` reminder. Example: `contextMessages`/`reminderText` in `src/reminders.ts` and `foldBranchAt` in `src/branch.ts` emit `You stopped with N incomplete todo item(s): … (Reminder 1/3)`.
  - Deferred cut-off nudge — Does: nudges a main-session settle that ended cut off (provider error, outstanding tool calls, non-human abort — never the user's own interrupt) after a 10-second grace when the host's `todo.reminders` is on and fewer than `todo.remindersMax` plugin reminders followed the latest real user message; the nudge is cancelled the moment a turn, queued message or editor draft appears, and latched so a stalled chain is nudged once until progress re-arms it. The host does not remind on such stops. Nothing is armed — no grace nudge, no quota wait or widget — while the project config sets `effects.cutOff` to `false` or is invalid (logged as a warning); the host's stop reminder and its text rewrite are unaffected. When: armed on `agent_end` of a main session. Example: `armCutOff`/`CUT_OFF_GRACE_MS`/`continuation` in `src/reminders.ts`, cancelled by `agent_start`, `session_shutdown`, `session_switch`, `session_branch`, `session_tree`.
  - Quota-429 wait — Does: defers the cut-off reminder until one minute past the account reset on a usage-limit 429 (provider retry hint, else omp's estimate of 30 min for an exhausted quota), shows a one-line above-editor widget with the send time, and holds the reminder while a draft sits in the editor. When: inside the cut-off wait decided at `agent_end`. Example: `cutOffWait`/`quotaNoticeLine` in `src/quota-wait.ts` render `Todo reminder scheduled for 14:35 (account quota 429, resets 14:34) · Ctrl+N or /todo-ng-cancel to cancel`, widget key `todo-ng.quota-reminder`.
  - `/todo-ng-cancel` and `Ctrl+N` — Does: registers the command and the shortcut to cancel the pending deferred reminder, latching the chain and notifying `Todo reminder cancelled` or `No pending Todo reminder`. When: when the user presses `Ctrl+N` or runs `/todo-ng-cancel`. Example: `pi.registerShortcut("ctrl+n", …)` and `pi.registerCommand("todo-ng-cancel", …)` in `src/reminders.ts`.
  - Mid-run nudge content — Does: when the host sends its mid-run todo nudge (`todo.midRunNudges` `capped` or `backoff`, after 12 or more mutating tool results without a `todo` call), replaces the text with one that lists the open count and the goal. When: in the `context` hook, on a message of type `mid-run-todo-nudge`. Example: `midRunNudgeText` in `src/reminders.ts` emits ``N todo items still open. If you finished a task since last `todo` update, mark it done now…``.
  - Goal-mode `<todo_context>` — Does: replaces the host's todo snapshot inside each `goal-mode-context` message that carries one with the plugin's richer snapshot (goal, status, explanation, estimate) as of that message's place in the branch. When: in the `context` hook on every model call while such a message is in context. Example: `contextMessages`/`goalTodoContext` in `src/reminders.ts`.
  - Reminder renderer — Does: renders reminder events as a bare header line (incomplete count · attempt/max) so the transcript card never re-lists the todo items. When: when the transcript renders an `mouriya.omp.todo-more.reminder` message. Example: `pi.registerMessageRenderer(REMINDER_TYPE, renderReminder)` in `src/reminders.ts`.
- **Overtime warnings**
  - Overtime deadline timer — Does: keeps one timer aimed at the nearest active item's estimate deadline, read from the live host list with the notes' clocks, re-armed on session/branch events, `todo`/`ask` results and turn/run ends, and standing down while an `ask` is open. No timer is kept and no warning is sent while the project config sets `effects.overtime` to `false` or is invalid (logged as a warning). When: scheduled from `session_start`/`session_switch`/`session_branch`/`session_tree` and every list-changing event. Example: `registerOvertime`/`reschedule` in `src/overtime.ts`.
  - Overtime warning delivery — Does: at the deadline sends one `mouriya.omp.todo-more.overtime` message per budget id — an aside mid-run, a visible no-turn message while idle — wrapped in a `<system-reminder source="omp-todo-ng/overtime">` delta carrying the current clock time and the missed target completion clock time, with the recorded message as the durable warning fact the branch folds. When: when a tracked item's in_progress wall time passes its estimate. Example: body `Current time: 2026-11-22 10:31\nSERIOUS: todo item "…" is past its target completion time of 10:30 (overdue as of 10:31).` in `src/overtime.ts`, sent with `createDeltaStream("omp-todo-ng/overtime")`.
- **Native UI and Tern panel**
  - `todo-ng.hud` widget — Does: mounts a live `TodoHud` above the editor, where omp places it directly before its activity line, following the viewed session — pill, progress and a disclosure opening the rich popover — and re-installs on session, branch and tree transitions. When: on `session_start`/`session_switch`/`session_branch`/`session_tree`. Example: `installHud`/widget key `todo-ng.hud` in `src/ui.ts`.
  - `/todo` input rewrite — Does: rewrites interactive `/todo` and `/todo edit` input to `/todo-ng` on a native frontend, leaving the other `/todo` subcommands to the host. When: on `input` events matching `/^\/todo(?:[\s:]+(.*))?$/` when native rendering is active. Example: the `input` hook in `src/ui.ts` returns `{ text: "/todo-ng" }`.
  - `/todo-ng` command and editor — Does: registers the command that opens the session-bound overlay editor (`TodoPanel`) for goal fields and item explanations, rejecting non-interactive sessions with a `todo-ng.ui-unavailable` message and discarding drafts when the viewed session changes. When: on `/todo-ng`, the HUD edit affordance or the `/todo` rewrite. Example: `pi.registerCommand("todo-ng", …)`/`TodoPanel` in `src/ui.ts`, message `Todo NG editor requires an interactive UI.`
  - Tern bundle — Does: ships `tern/plugin.toml` (id `omp-todo-ng`), `window.luau` and `todo-ng.css`, whose stylesheet lays the extension's widget row over omp's activity line and hides the native Todo HUD there while keeping its layout box, so the pill takes the native pill's place without adding a row or changing Tern's flex dock; with no activity line shown, the row keeps a line of its own. When: while the Tern plugin is installed and enabled. Example: the `.sf-dock[data-surface="omp.session"]` rules in `tern/todo-ng.css`.
  - Tern owner-CLI install — Does: installs or repairs the bundle through `tern plugin dir/list/install --json` at load, skipping a matching copy and rejecting the extension factory when Tern is present but the check fails. When: inside the async factory before the review API is subscribed; skipped when `tern` is not on `PATH`. Example: `initializeTernPlugin`/`isCurrent` in `src/tern-plugin-install.ts`.
- **Synchronous review protocol**
  - `omp-todo-ng:read` listener — Does: answers event-bus requests `{agentId, reply(value)}` synchronously from the named agent's live branch with `{kind: "ok", goal, openItems, counts}` or `{kind: "unavailable"}`, with no writes, cache or timers. When: whenever another in-process extension emits `omp-todo-ng:read` on `pi.events`; removed on `session_shutdown`. Example: `registerReviewApi` in `src/review-api.ts`, protocol in `omomp-shared/todo-read.ts`.
- **Plugin settings and project config**
  - Plugin settings — Does: declares `leafMaxMinutes` (default `60`, 1–1440) as a native plugin setting, an invalid value falling back to the default with a warning; the todo reminders, their limits and the eager prelude follow the host's `todo.*` settings. When: re-read via `getPluginSettings` on each `todo` call. Example: `omp.settings` in `package.json`, `readSettings` in `src/settings.ts`; set with `omp plugin config omp-todo-ng`.
  - Project config file — Does: reads the project's `.omp/todo-ng.json` from the git root of the session directory (the session directory itself outside git; parent directories are never merged) and parses it strictly: `effects` (`editGate`, `commit`, `overtime`, `cutOff`, each default `true`) and `tailItems` (unique `id` and `title`, `detail`, optional `phase` default `Verification`, `minutes` 1–1440, `scope` `main`/`isolated`/`all` default `main`, `protected` default `true`, `check` `{ kind: "shell", command, timeoutMs ≤ 600000 (default 120000) }` or `{ kind: "judge", prompt, timeoutMs ≤ 300000 (default 30000) }`); no file means all defaults. A file that cannot be read, is not JSON, carries an unknown key or a value out of range, or repeats a tail item `id` or `title` makes every `todo` change fail and every `edit` call blocked with the file path and the reason, logged as a warning, while `todo({})` and `todo({ view })` still answer with the same reason appended; overtime warnings and the cut-off nudge stay off until it parses. `leafMaxMinutes` stays a plugin setting. When: read again on every `todo` call, every `edit` `tool_call`, every subagent model call, every overtime reschedule and every cut-off check, so an edit to the file applies at the next of them. Example: `readProjectConfig` in `src/project-config.ts`, error `Project config /repo/.omp/todo-ng.json is invalid: effects.editgate: must be removed. Fix or remove the file: todo changes are refused until it parses.`
- **Language resolution**
  - UI text language — Does: resolves every human-facing string (tool labels, command descriptions, HUD, editor, notices) to English or Chinese from `OMOMP_LANG`, then `LC_ALL`/`LC_MESSAGES`/`LANG`, else English, re-read on each generation while model-facing text stays English. When: whenever the plugin emits UI text or registers labels. Example: `tr("Cancel the pending Todo NG reminder", "取消待发的 Todo NG 提醒")` in `src/reminders.ts`, `tr` from `omomp-shared/i18n.ts`.
