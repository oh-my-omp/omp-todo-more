# omp-todo-more

English | [简体中文](README.zh-CN.md)

- **The `todo` tool**
  - `todo` tool registration — Does: registers a tool named `todo` that shadows the host's built-in tool, accepting a flat JSON object (`goal`, `add`, `start_id`, `explain`, `estimate`, `done_id` with an optional `commit`, `drop_ids`, or `view`) over a phased list with a goal, stable item IDs (`t1`, `t2`, …), per-item explanations, minute budgets and per-status progress times. Calling `todo({})` or `todo({ view })` inspects the full, current, or single-phase tree read-only; mutations return a compact active view with IDs, the current clock time and the active item's target completion time. When: whenever the model calls `todo` in a session where the plugin is loaded. Example: `pi.registerTool(TODO_TOOL_DEFINITION)` in `index.ts`; inspect with `{}` / `{ view: "current" }`, or mutate with `{ goal: { title, summary, acceptance }, add: [{ phase, title, detail, minutes }] }`.
  - Tool field declarations — Does: declares `loadMode: "essential"`, `approval: "read"` (Plan Mode compatible), `concurrency: "exclusive"` and `mergeCallAndResult: true`, so the tool is always available, serialized and its result card replaces the call card. When: fixed at tool registration on plugin load. Example: `TOOL_FIELDS` in `index.ts`.
  - Description and card rendering — Does: carries a concise (<=200-char) description summarizing phased work, the per-item `leafMaxMinutes` limit, and `todo({})` / `todo({ view })` inspection, plus `describeCall`/`describeResult` and `renderCall`/`renderResult` hooks that paint ANSI and native cards previewing the structured arguments and delta/full state. When: in the tools section of the prompt whenever `todo` is offered, and when a `todo` call or result card renders. Example: `DESCRIPTION` in `src/tool.ts`, `renderTodoCall`/`renderTodoResult` from `src/render.ts`.
  - Batch validation — Does: validates the entire call atomically before applying anything: non-empty goal/task fields, unique titles, positive integer `minutes` capped by `leafMaxMinutes` (default 60), valid IDs, `commit` only alongside a `done_id` that completes an open item, and `estimate` refused on an item that already received an overtime warning. When: on every `todo` call, before any state change. An `add` allocates its IDs before validation, so the same call's `start_id`, `explain`, `estimate`, `done_id` and `drop_ids` may name them. Example: `validate`/`overCap` in `src/tool.ts` produce `Task "…" estimate 90 min exceeds the 60-minute limit for one item`.
- **Completion commits**
  - Commit on completion — Does: `done_id` completes one item per call, because one completion owes at most one commit; its `commit.message` commits the changes the host's change record attributes to this agent and its subagents, or with `commit.paths` every change in those git pathspecs resolved from the session directory, through the host's selective commit on a private index so another writer's staged or unstaged changes stay where they are, and records `{sha, message, scope}` on the item. The commit runs after every other field of the call passed validation; a failed commit rejects the whole call and leaves the item open. When: on a `todo` call whose `done_id` completes an open item. Example: `{ done_id: "t2", commit: { message: "feat: add export", paths: ["src/export.ts"] } }` → `Committed 1a2b3c4 "feat: add export" (src/export.ts)`, via `completeWithCommit` in `src/tool.ts` and `commitCompletion` in `src/git.ts`.
  - `Model:` trailers — Does: appends one `Model: <provider>/<id>` trailer per model that answered in the session since its previous todo commit, in order of first use, plus the current model. When: on every commit a completion makes. Example: `commitMessage`/`participatingModels` in `src/models.ts` write `Model: anthropic/claude-opus-5-5`.
  - Uncommitted-work refusal — Does: rejects a `done_id` without `commit` while this agent has uncommitted changes in the checkout, or while the session keeps no change record and the checkout is dirty; another writer's changes alone never trigger it. When: on a `todo` call whose `done_id` completes an open item without `commit`. Example: `workState` in `src/git.ts`, error `Task "Implement" (t1) would leave this agent's uncommitted work in /repo: call todo again with commit ({ message }) …`.
  - Shared-worktree exemption — Does: lets a subagent whose cwd is in its parent agent's git worktree complete items without committing or the refusal, any `commit` ignored, so the parent integrates and commits; a subagent in its own linked worktree commits normally. When: on every completion of a subagent whose parent session resolves through `AgentRegistry`. Example: `parentCwdOf` in `index.ts`, `sharedWorktreeRoot` in `src/git.ts`, note `Shared worktree with the parent agent (/repo): this completion committed nothing; …`.
- **List state on the session branch**
  - Host list and notes — Does: keeps the list's phases, titles, order and statuses only in the host list (`session.getTodoPhases()` live; on the branch, the latest `todo` result's `details.phases`, or the `user_todo_edit` entry the host records in place of a `todo` result when the tool is called from eval) and records only what the host list cannot hold — goal, item IDs, explanations, estimates, progress times and commit records — as a `mouriya.omp.todo-more.notes` entry joined to host items by phase name and title once, at the join; everything after the join identifies items by ID; a `todo` call writes the host list and appends a notes entry only when the notes changed; a `/todo-more` save does the same (`commitTodoState`), the host list's content staying as it was since an edit changes only goal or explanations. Readers that act between a `todo` call's end and its result reaching the branch (the empty-list `edit` gate, the planning snapshot, the review read, the stop-time reminder check, the content of a host reminder not yet persisted) read `liveState`, and so do the `/todo-more` panel and HUD. A `todo` result's `details.more` snapshot only feeds its own card. When: after every accepted `todo` call and `/todo-more` save. Example: `commitTodoState`/`liveState` in `src/commit.ts`, `joinHost`/`toNotes` in `src/state.ts`.
  - Branch fold — Does: folds every read forward over the branch entries — the latest host list, from a `todo` result or a `user_todo_edit` entry, joined with the latest notes entry by phase name and title, giving a host item without notes a fresh ID and no explanation or estimate — together with ask waits, overtime warnings and the planning deliveries, keeping one incremental accumulator per session manager. When: on every read of the list by reminders, the UI and the overtime facts. Example: `foldEntry`/`branchFacts` in `src/branch.ts`.
  - Time tracking — Does: tracks per-item `in_progress` wall time with `ask` waits excluded, keeps each item's progress in a form fixed by its status (pending: first start and pause time; in progress: first start and running clock; completed or abandoned: first start and close time), converts a started item's remaining budget into a target completion clock time (`due by HH:MM`, pausing on skip/preemption and reconverting remaining budget on resume while leaving unstarted items without a deadline), and records a budget id per estimate so an overtime warning latches to that budget identity across re-estimates. When: during each branch fold, transition settlement and overtime check. Example: `elapsedOf`/`dueAt`/`transition` in `src/state.ts`, `itemTimeSummary` in `src/format.ts`, waits folded from `tool_execution_start` records in `src/branch.ts`.
- **`todo` restoration in editing subagents**
  - Subagent `todo` restoration — Does: puts `todo` back into a subagent session whose enabled tools include `edit` but not `todo`, writing the active set in canonical order (builtins in registry order, then the rest sorted by code point) so forks keep the prompt cache; tool-restricted sessions get it via `refreshRpcHostTools`. When: before every model call of a subagent session, via a before-model-call hook armed on its first `before_agent_start`. Example: `guardSubagent`/`restoreTodo` in `index.ts`, with `canonicalToolOrder` from `omomp-shared/active-tools.ts`.
- **Planning and reminders**
  - Eager prelude content — Does: when the host's `todo.eager` (`preferred` or `always`) makes it emit its hidden eager prelude, replaces the text with the plugin's structured `todo` call instruction (`goal` and `add` with `phase`, `title`, `detail`, `minutes`); the host owns when it appears, including after an auto-compaction. When: in the `context` hook, on a message of type `eager-todo-prelude`. Example: `eagerTodoText`/`hostReminderOf` in `src/reminders.ts`, text ``Before substantive work, create a phased todo. … You MUST call `todo` first in this turn.``.
  - Edit guard — Does: blocks an `edit` call from the host's `tool_call` event while the todo list is empty, giving the init reminder as the reason, without touching the host's `edit` tool. A `todo` call that precedes the `edit` in the same assistant message — the host emits every `tool_call` of a message before executing any of them — counts when its arguments pass `todo`'s own schema and rule checks and leave a non-empty list; the call is only previewed, never executed. When: on every `edit` `tool_call` of a main session or subagent; the earlier `todo` calls are checked on their own `tool_call`. Example: `registerPlanning` in `src/planning.ts` blocks with `Todo is empty. Work phase … call todo with goal`, `previewTodo` in `src/tool.ts` runs the shared schema and rule checks.
  - Planning reminder — Does: delivers a `<system-reminder source="omp-todo-more/planning">` carrying the current clock time — the `goal` + `add` instruction while empty, a compact active view (goal, progress, closed phase counts, `in_progress` full explanation and target completion time, plus `pending` IDs/titles and `todo({})` / `todo({ view })` hints) when semantic state changed before a user prompt or after an out-of-band `/todo-more` edit (highlighting edited pending explanations), and the complete unabridged plain-text list once after compaction or branch transition drops prior context — skipping duplicate injection after `todo`'s own tool results and ignoring wall-clock ticks when semantic state is unchanged. Each delivery appends a `mouriya.omp.todo-more.planning` entry with the delivered state's key; the branch fold reads those entries, compaction and branch-summary entries and `todo` results to decide what the model last saw and whether recovery is due. When: as a hidden `before_agent_start` message when semantic state changed or context was compacted, and as `tool_result` `additionalContext` only for mid-run compaction recovery or out-of-band edits. Example: `registerPlanning` in `src/planning.ts`, `semanticStateKey` in `src/state.ts`, `foldPlanning` in `src/branch.ts`, `formatCompactView`/`formatFullView` in `src/format.ts`.
  - Stop reminder content — Does: when the host sends its stop reminder (`todo.reminders`, at most `todo.remindersMax` times, main session and subagents alike), replaces the text with the plugin's: current clock time, every open item with its ID, explanation and clock-time status (`due by` for active, `paused` for preempted, no deadline for unstarted), the goal (or a prompt to pass `goal`) and an `explain` hint for items without an explanation. The text comes from the list and message timestamp as they stood where the reminder sits in the branch, so it keeps its bytes on later requests. When: in the `context` hook, on a developer message shaped like the host's `You stopped with N incomplete todo item(s)` reminder. Example: `contextMessages`/`reminderText` in `src/reminders.ts` and `foldBranchAt` in `src/branch.ts` emit `You stopped with N incomplete todo item(s): … (Reminder 1/3)`.
  - Deferred cut-off nudge — Does: nudges a main-session settle that ended cut off (provider error, outstanding tool calls, non-human abort — never the user's own interrupt) after a 10-second grace when the host's `todo.reminders` is on and fewer than `todo.remindersMax` plugin reminders followed the latest real user message; the nudge is cancelled the moment a turn, queued message or editor draft appears, and latched so a stalled chain is nudged once until progress re-arms it. The host does not remind on such stops. When: armed on `agent_end` of a main session. Example: `armCutOff`/`CUT_OFF_GRACE_MS`/`continuation` in `src/reminders.ts`, cancelled by `agent_start`, `session_shutdown`, `session_switch`, `session_branch`, `session_tree`.
  - Quota-429 wait — Does: defers the cut-off reminder until one minute past the account reset on a usage-limit 429 (provider retry hint, else omp's estimate of 30 min for an exhausted quota), shows a one-line above-editor widget with the send time, and holds the reminder while a draft sits in the editor. When: inside the cut-off wait decided at `agent_end`. Example: `cutOffWait`/`quotaNoticeLine` in `src/quota-wait.ts` render `Todo reminder scheduled for 14:35 (account quota 429, resets 14:34) · Ctrl+N or /todo-more-cancel to cancel`, widget key `todo-more.quota-reminder`.
  - `/todo-more-cancel` and `Ctrl+N` — Does: registers the command and the shortcut to cancel the pending deferred reminder, latching the chain and notifying `Todo reminder cancelled` or `No pending Todo reminder`. When: when the user presses `Ctrl+N` or runs `/todo-more-cancel`. Example: `pi.registerShortcut("ctrl+n", …)` and `pi.registerCommand("todo-more-cancel", …)` in `src/reminders.ts`.
  - Mid-run nudge content — Does: when the host sends its mid-run todo nudge (`todo.midRunNudges` `capped` or `backoff`, after 12 or more mutating tool results without a `todo` call), replaces the text with one that lists the open count and the goal. When: in the `context` hook, on a message of type `mid-run-todo-nudge`. Example: `midRunNudgeText` in `src/reminders.ts` emits ``N todo items still open. If you finished a task since last `todo` update, mark it done now…``.
  - Goal-mode `<todo_context>` — Does: replaces the host's todo snapshot inside each `goal-mode-context` message that carries one with the plugin's richer snapshot (goal, status, explanation, estimate) as of that message's place in the branch. When: in the `context` hook on every model call while such a message is in context. Example: `contextMessages`/`goalTodoContext` in `src/reminders.ts`.
  - Reminder renderer — Does: renders reminder events as a bare header line (incomplete count · attempt/max) so the transcript card never re-lists the todo items. When: when the transcript renders an `mouriya.omp.todo-more.reminder` message. Example: `pi.registerMessageRenderer(REMINDER_TYPE, renderReminder)` in `src/reminders.ts`.
- **Overtime warnings**
  - Overtime deadline timer — Does: keeps one timer aimed at the nearest active item's estimate deadline, read from the live host list with the notes' clocks, re-armed on session/branch events, `todo`/`ask` results and turn/run ends, and standing down while an `ask` is open. When: scheduled from `session_start`/`session_switch`/`session_branch`/`session_tree` and every list-changing event. Example: `registerOvertime`/`reschedule` in `src/overtime.ts`.
  - Overtime warning delivery — Does: at the deadline sends one `mouriya.omp.todo-more.overtime` message per budget id — an aside mid-run, a visible no-turn message while idle — wrapped in a `<system-reminder source="omp-todo-more/overtime">` delta carrying the current clock time and the missed target completion clock time, with the recorded message as the durable warning fact the branch folds. When: when a tracked item's in_progress wall time passes its estimate. Example: body `Current time: 2026-11-22 10:31\nSERIOUS: todo item "…" is past its target completion time of 10:30 (overdue as of 10:31).` in `src/overtime.ts`, sent with `createDeltaStream("omp-todo-more/overtime")`.
- **Native UI and Tern panel**
  - `todo-more.hud` widget — Does: mounts a live `TodoHud` above the editor, where omp places it directly before its activity line, following the viewed session — pill, progress and a disclosure opening the rich popover — and re-installs on session, branch and tree transitions. When: on `session_start`/`session_switch`/`session_branch`/`session_tree`. Example: `installHud`/widget key `todo-more.hud` in `src/ui.ts`.
  - `/todo` input rewrite — Does: rewrites interactive `/todo` and `/todo edit` input to `/todo-more` on a native frontend, leaving the other `/todo` subcommands to the host. When: on `input` events matching `/^\/todo(?:[\s:]+(.*))?$/` when native rendering is active. Example: the `input` hook in `src/ui.ts` returns `{ text: "/todo-more" }`.
  - `/todo-more` command and editor — Does: registers the command that opens the session-bound overlay editor (`TodoPanel`) for goal fields and item explanations, rejecting non-interactive sessions with a `todo-more.ui-unavailable` message and discarding drafts when the viewed session changes. When: on `/todo-more`, the HUD edit affordance or the `/todo` rewrite. Example: `pi.registerCommand("todo-more", …)`/`TodoPanel` in `src/ui.ts`, message `Todo More editor requires an interactive UI.`
  - Tern bundle — Does: ships `tern/plugin.toml` (id `omp-todo-more`), `window.luau` and `todo-more.css`, whose stylesheet lays the extension's widget row over omp's activity line and hides the native Todo HUD there while keeping its layout box, so the pill takes the native pill's place without adding a row or changing Tern's flex dock; with no activity line shown, the row keeps a line of its own. When: while the Tern plugin is installed and enabled. Example: the `.sf-dock[data-surface="omp.session"]` rules in `tern/todo-more.css`.
  - Tern owner-CLI install — Does: installs or repairs the bundle through `tern plugin dir/list/install --json` at load, skipping a matching copy and rejecting the extension factory when Tern is present but the check fails. When: inside the async factory before the review API is subscribed; skipped when `tern` is not on `PATH`. Example: `initializeTernPlugin`/`isCurrent` in `src/tern-plugin-install.ts`.
- **Synchronous review protocol**
  - `omp-todo-more:read` listener — Does: answers event-bus requests `{agentId, reply(value)}` synchronously from the named agent's live branch with `{kind: "ok", goal, openItems, counts}` or `{kind: "unavailable"}`, with no writes, cache or timers. When: whenever another in-process extension emits `omp-todo-more:read` on `pi.events`; removed on `session_shutdown`. Example: `registerReviewApi` in `src/review-api.ts`, protocol in `omomp-shared/todo-read.ts`.
- **Plugin settings**
  - Plugin settings — Does: declares `leafMaxMinutes` (default `60`, 1–1440) as a native plugin setting, an invalid value falling back to the default with a warning; the todo reminders, their limits and the eager prelude follow the host's `todo.*` settings. When: re-read via `getPluginSettings` on each `todo` call. Example: `omp.settings` in `package.json`, `readSettings` in `src/settings.ts`; set with `omp plugin config omp-todo-more`.
- **Language resolution**
  - UI text language — Does: resolves every human-facing string (tool labels, command descriptions, HUD, editor, notices) to English or Chinese from `OMOMP_LANG`, then `LC_ALL`/`LC_MESSAGES`/`LANG`, else English, re-read on each generation while model-facing text stays English. When: whenever the plugin emits UI text or registers labels. Example: `tr("Cancel the pending Todo More reminder", "取消待发的 Todo More 提醒")` in `src/reminders.ts`, `tr` from `omomp-shared/i18n.ts`.
